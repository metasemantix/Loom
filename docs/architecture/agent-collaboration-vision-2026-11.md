# Loom product vision and agent collaboration roadmap

17 November 2026 · [Reviewed main at `9f64465`](https://github.com/metasemantix/Loom/commit/9f6446562005ae4395da5cff444438eb64f5c7ba) · [Architectural trajectory review, merged in PR #45](https://github.com/metasemantix/Loom/pull/45)

**Build a collaboration loop people can use twice.** A project owner connects an external agent to one working document. The agent reads the current revision, prepares a change, applies it with the human's instruction, and retrieves the result. Loom shows who changed what. In another session the agent picks up the latest document and its outstanding work without a transcript or a pasted payload. Start with a project-level agent panel and one version-checked write. The second session is the product test.

## 2. Proposed human–agent experience

**Demo project — a workshop runbook.** The owner creates a project and a native Markdown document called “Workshop runbook.” It contains an agenda, confirmed logistics, and an “Open questions” section. The project is readable by its human members so they can inspect edits. One person and one named agent are enough to run the demo.

1. **Connect.** From the project, the owner selects the runbook and creates or selects an agent called “Workshop assistant.” The panel summarizes the scope in plain language and issues a time-limited read/edit credential. The owner connects it to the agent's external runner through that runner's secret settings. This is the first agent invitation experience. It grants project participation through a scoped credential and requires no Discord identity or agent account ceremony.
2. **Do a useful edit.** The human asks the agent to reflect a move to Room B at 14:30, adjust the setup checklist and flag the still-unconfirmed projector. The runner discovers the authorized project and document, retrieves the current body, and shows a preview of its proposed edits. The human asks it to apply the change. The runner sends a conditional update and fetches the new revision. Preview and confirmation are part of this demo client's interaction. The grant itself permits direct edits within scope, so Loom should make that fact visible during connection.
3. **Inspect in Loom.** The project's recent activity and the runbook history identify “Workshop assistant,” the revision, the time and a short change note. The human opens the before and after revisions, verifies the agenda, and sees the projector question preserved. A conflict during the edit keeps the newer human revision visible and prompts another preview after the agent reloads.
4. **Resume with fresh conversation context.** The human closes the external session and edits another detail in Loom. In a fresh session they ask the same configured agent to continue the runbook. Its runner retains a secret reference, and Loom supplies the project, current revision and open questions. If the old credential has expired, the owner issues a fresh one for the same agent record. The new credential continues the same attribution and sees the current body.
5. **Stop.** The owner revokes the grant and observes the runner's next read and write fail. Existing revision attribution remains visible. A completed download remains in the recipient's possession.

The runbook makes persistence visible without introducing a task engine. A “what changed and what remains open” section can serve as a handoff to the next session. Test it with a real working document and a real human correction between runs. A scripted fixture proves plumbing, while a genuine correction tests whether the agent resumes usefully.

## 3. Agent dashboard concept

**Start with an Agents section on the project.** Extend the existing owner credential controls. Show the agent name, current scoped authorizations and their state, and the most recent attributable edit with a link to the revision. The owner's main actions are **Connect agent**, **Issue replacement**, **Revoke** and **Open activity**. Show the token once, with copyable runner setup that describes the destination separately from the secret. Human project readers can see attributable changes through existing history. Reserve credential management and any detailed access audit for authorized managers. A consolidated dashboard becomes useful when owners regularly lose track of agents across projects. At that point derive its rows from agent records, project associations and grants filtered by the viewer's authority. Avoid a separately maintained inventory or activity store. Use explicit account linking if project-local agents later need a shared identity.

## 4. End-to-end read/write collaboration design

### Identity and authority

For the pilot, a project owner registers a project-local agent record. Its stable ID represents the collaboration role the owner connected and survives ordinary credential replacement. Store the issuing participant, selected native document, allowed actions, expiry and revocation on credential/grant records. A bearer can authenticate the acting credential and resolve its grant and agent ID. Possession establishes use of the credential, with no claim about which model or operator was behind it. Keep the secret hash-only in Loom, use an Authorization header, and keep secrets outside agent prompts and document history. Reuse the existing credential table and manager if the new fields can preserve legacy behavior and enforce scoped grants by construction. A separate grant table can wait until a real use case needs multiple credentials per grant or multiple resources per grant. ### Request and commit sequence

| Step | Reuse | Add for the pilot |
| --- | --- | --- |
| Connect or resume | Existing owner-only issuance/revocation and machine introspection. | Select the target native document, create or reuse the agent record, issue the expiring bearer, and resolve the stable agent ID and effective permission on introspection. Rotation leaves history attributable and explicitly revokes the replaced bearer. |
| Discover and read | `GET /api/agent/me`, `GET /api/agent/project`, `GET /api/agent/documents`, and the authorized item GET. | Filter the list, metadata and body to the selected target for scoped bearers. Return an opaque current revision ID. Existing credentials retain their existing rights. Check-in and all ungranted operations remain unavailable to the new scoped credential. |
| Preview and apply | Existing native document validation, revision IDs and immutable history. | Add a machine PUT on the item route, or a dedicated equivalent. Accept a complete body, content type, expected revision ID and a bounded change note. The owner opts into direct, conditional edits of that document only. The runner previews locally, then applies on instruction. No server-side proposals inbox is needed for this trial. |
| Verify and continue | Item retrieval and human revision history. | Return the committed revision ID and surface stable agent attribution plus credential/grant provenance. Teach the runner to fetch the head after success and after an ambiguous response. A replay of a successful request using the old base must create no second revision. Compare the current head with the intended outcome before another attempt. Add request IDs later if the client needs an unambiguous retry receipt even after intervening changes. |

The decisive D1 write should check the live credential, expiry, exact resource and action, active project state, relevant deadline, and current revision together. Store the revision, head and provenance atomically. Reuse the semantic mutation across human and machine paths while preserving their respective authorization checks and existing callers. Add a revision precondition to the browser editor serving the pilot. Render agent provenance in native history and project activity, and preserve actor type wherever revision provenance is exported. A stale write should return a conflict, preserve the editor's local work, and trigger an explicit re-read/review. The scoped read queries should likewise enforce live authorization at the content boundary. Target the deletion and revocation cases from PR #45 that affect this route. ## 5. Three-horizon roadmap

| Horizon | Concrete features and reuse | Required work and dependencies | Demonstrable success |
| --- | --- | --- | --- |
| **A · First working collaboration** | Project-level connection, one native document, one external runner, conditional apply, visible authorship and a second session. Reuse owner-issued bearers, discovery, native history and the project page. | Scoped expiring grants, a stable agent record, a shared revision precondition, machine write, provenance display and one runner adapter. Requires a real owner, one document and the affected deletion/revocation checks. | Agent reads and edits, human verifies, human changes the file, agent resumes with fresh context. Stale writes and revoked, expired or wrong-document grants cannot change the document. |
| **B · Usable participation** | Multiple agent connections across working projects, better renewal and rotation, recent activity, conflict recovery and optional read receipts. Reuse agent/grant projections, machine audit and history. | Improve onboarding after observing setup failures. Define explicit ownership-transfer behavior and authorization for audit views. Add stored proposals only if human review repeatedly blocks direct delegation. Consider broader discovery across projects after users need it. | A second owner connects a runner unaided, can explain its access, finds a change and removes access. Two participants can make overlapping edits without silent data loss. |
| **C · Emerging ecosystem** | Opt-in published projects, portable project references, distinct interoperating clients, and multiple agents sharing work through project artifacts. Reuse project ownership, publication projections, document revisions and attribution. | Publication consent and retention, an external contract with a real client, and explicit handoff and reconciliation semantics. Introduce scheduling, richer agent principals or real-time editing only when measured demand warrants it. | A second client resumes the same project workflow with current data and equivalent policy. Different agents hand off work through persistent artifacts, and a public reader can access the intentionally published projection only. |

## 6. Recommended next sprint

### 1. Connect a named agent to one project document · Medium

- **User-visible outcome.** The project owner can connect “Workshop assistant” to the runbook and later replace or revoke its connection.
- **Backend and frontend.** Add a project-local agent record and an expiring, single-native-resource grant option. Extend credential management and introspection, scope machine discovery and retrieval, and extend the project credentials panel with a target picker, permission summary, expiry and copy-once setup. Reuse issuance, hashing, revocation and retrieval. Allow an edit-capable option only when the corresponding route is available.
- **Dependencies.** Decide sponsor versus project ownership for the agent record, a fixed pilot expiry default, and the behavior on ownership transfer. Establish the affected lifecycle predicates and preserve legacy semantics during migration.
- **Acceptance.** Owner can connect without creating a human membership. All machine projections exclude other bodies and metadata, including linked sources. Nonowners cannot issue. Expired/revoked grants fail. Replacement resolves to the same agent ID. Legacy grants and check-ins behave as before.

### 2. Write one agent-attributed revision and inspect it · Medium to large

- **User-visible outcome.** The agent applies a change and retrieves the new head. The human sees an attributable revision and can compare it with the previous body.
- **Backend and frontend.** Add a conditional machine write and an explicit browser save precondition, reusing native validation, revisions and D1 batches. Extend history and activity to render the agent and change note. Preserve existing history and export attribution. Show a conflict in the editor without losing unsaved input.
- **Dependencies.** Task 1's grant contract, and the cutoff and commit-time authorization rules for this specific read/write path. Implement against fixtures before enabling the pilot grant.
- **Acceptance.** A valid write produces exactly one revision and activity entry. A stale base, repeated submission with the same base, wrong scope, revoked/expired grant, or unavailable project creates no revision. A human sees before/after contents and the correct actor. A grant changed during request processing cannot authorize the eventual commit.

### 3. Run a real two-session collaboration · Small to medium

- **User-visible outcome.** An owner can follow one setup recipe and resume the same collaboration after closing the first session.
- **Backend and frontend.** Use the existing HTTP endpoints from a single local or server-side tool adapter. Add concise setup and troubleshooting to the project section or linked doc. The runner needs secret configuration, discover/read, preview/apply and refresh operations. No additional service endpoint is required if tasks 1 and 2 deliver the agreed interface.
- **Dependencies.** A chosen runner with secure secret storage and HTTP tools, tasks 1 and 2, and a real disposable or low-stakes workshop project.
- **Acceptance.** Record a human instruction, first agent edit, human correction, and successful fresh-session continuation without pasted project content. Demonstrate a conflict and revocation. Record where the human needed help and whether they willingly delegated a second edit. Use those observations to prioritize B.

## 7. Promising possibilities and what to test

- **A project handoff document** is the natural next experiment. A human asks one agent to update constraints and another to verify the plan against them. Revision IDs and a shared “open questions” section give both a reliable starting point. Test asynchronous handoff before adding agent messaging, agent-to-agent delegation or orchestration.
- **Public project reading** makes Loom useful to visiting agents before registration. Try a maintained resource such as a club runbook or a course project whose owners deliberately publish selected pages. Measure whether visitors retrieve them and return. Public contribution, durable membership and private editing can remain distinct product choices. - **A dashboard may be unnecessary beyond the project page.** Observe whether users begin with an agent or begin with a document. ## 8. Open product decisions

1. Who is the first owner of a real pilot document, and what repeatable task would they delegate twice?
2. Which runner offers the simplest secure connection? Can its setup feel like connecting an agent rather than copying credentials by hand?
3. Will direct edits with a client preview be acceptable, or should the first pilot use a server-enforced proposal? Which changes should always require human approval?
4. Does an agent record describe a project role, a particular external installation, or an assistant the owner expects to bring to several projects? What should happen to its grants when a project changes owners?
5. Which past actions will a human actually inspect? How much audit detail is appropriate for members and owners, and for how long?
6. What counts as a useful second session? Is returning to the current document enough, or do owners also need an explicit handoff note, open task or record of prior instructions?

This is a repository-based product design. The proposed runner, user journey, performance and adoption have not been tested. The cited implementation was inspected on the pinned baseline, where PR #45 is merged and the Lab threads proposal remains open.
