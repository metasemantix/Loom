# Loom architectural trajectory review

17 November 2026 · Review of `metasemantix/Loom` at [`b311632` on main](https://github.com/metasemantix/Loom/commit/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0).

## 1. Executive findings

- **Keep Loom's two ownership models.** A project can reference a participant's live document or own a document created or deliberately copied into it. This distinction makes retraction, exports, creator departure and project deletion intelligible. Preserve it when introducing publication or agent editing. [docs/PROJECT_NATIVE_DOCUMENTS.md:11–32](https://github.com/metasemantix/Loom/blob/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0/docs/PROJECT_NATIVE_DOCUMENTS.md#L11-L32) [docs/PROJECT_NATIVE_DOCUMENTS.md:143–177](https://github.com/metasemantix/Loom/blob/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0/docs/PROJECT_NATIVE_DOCUMENTS.md#L143-L177)
- **Consolidate authority before widening access.** Start with finalization, revocation and commit-time authorization in the existing Worker and D1 database. The shell finalizer appears to leave saved compression content behind. Some handlers establish authority in one query and rely on it in a later one. These are source findings, with consequences that warrant targeted tests. [src/project-deletion.ts:40–60](https://github.com/metasemantix/Loom/blob/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0/src/project-deletion.ts#L40-L60) [migrations/0011_compression_revisions.sql:1–20](https://github.com/metasemantix/Loom/blob/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0/migrations/0011_compression_revisions.sql#L1-L20) [src/agent-access.ts:39–69](https://github.com/metasemantix/Loom/blob/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0/src/agent-access.ts#L39-L69) [src/projects.ts:35–37](https://github.com/metasemantix/Loom/blob/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0/src/projects.ts#L35-L37)

A public project should carry no implicit right to read linked personal documents, historical versions, member details, activity or exports. Decide publication and contribution separately. [DECISIONS.md:33–46](https://github.com/metasemantix/Loom/blob/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0/DECISIONS.md#L33-L46) [DECISIONS.md:342–356](https://github.com/metasemantix/Loom/blob/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0/DECISIONS.md#L342-L356) [src/projects.ts:14–17](https://github.com/metasemantix/Loom/blob/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0/src/projects.ts#L14-L17)

## 3. Five consequential architectural assumptions

### 1. Project ownership and participant ownership can coexist indefinitely

**Evidence.** Ownership is persisted as `owner_type` and `owner_id`. Linking has its own state, and a copy is a distinct artifact. Versions, creator entitlement, exports and deletion depend on these choices. **Failure and cost.** Unified project membership or publication could accidentally override consent to disclose a linked source. A copy can legitimately survive source retraction, which becomes misleading if the UI or an integration treats it as a live link. Recovering original intent after flattening links and copies would require provenance backfills and may be impossible for older records. Published or exported copies create irreversible disclosure. **Recommendation.** Retain both forms. Require explicit, independently understood consent to publish or copy. **Early warning.** A supposedly public project automatically publishes newly linked documents, or a migration recasts linked document IDs as project-owned. [migrations/0007_project_native_documents.sql:11–52](https://github.com/metasemantix/Loom/blob/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0/migrations/0007_project_native_documents.sql#L11-L52) [src/project-documents.ts:12–23](https://github.com/metasemantix/Loom/blob/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0/src/project-documents.ts#L12-L23) [docs/PROJECT_NATIVE_DOCUMENTS.md:143–177](https://github.com/metasemantix/Loom/blob/b311632c8019c71ec9cc23f12bab2ca8ce80fcb0/docs/PROJECT_NATIVE_DOCUMENTS.md#L143-L177)

### 2. Membership and a project audience can carry the policy as operations multiply

**Evidence.** Existing policy combines roles, audience, lifecycle and actor state across the router and SQL handlers. Some decisive SQL statements recheck membership or lifecycle. For example, the role-change handler first resolves owner authority, then its UPDATE rechecks project state and target role without rechecking the caller's owner role. Machine read resolves credential state before fetching content. Human export resolves membership and audience ahead of the body query. **Failure and cost.** The same document can acquire inconsistent policy across list, detail, history, export, public projection and machine paths. For in-flight revocation, even the intended cutoff needs defining. A custom role per use case would also entwine editing, participation and governance, forcing a difficult membership and client migration. **Recommendation.** Revise now. Define one operation matrix with explicit actors, resources, state, read layers and commit conditions. Reuse it through transport-specific adapters and authoritative SQL guards. Start with fixed operations and project-level roles. **Early warning.** A new endpoint copies a predicate and omits a lifecycle or grant condition, or an interface hides a button while the underlying API still permits action. ### 3. A credential or capability chain supplies enough attribution

**Evidence.** The machine credential couples label, authenticator and project grant. It has no expiry field or independent agent subject. Check-ins reference the credential ID. Lab continuity makes a narrower claim about possession, including on re-entry, and explicitly excludes cross-interface identity. **Failure and cost.** Rotation breaks apparent agent continuity, copying a token collapses distinct operators into a single audit identity, and credential survival through ownership changes may surprise incoming owners. Today the grant lookup follows the project and credential state, without rechecking the original issuer's role. Inferring earlier operators after the fact is generally impossible. Mapping existing rows as legacy grants is feasible while agent activity remains bounded. **Recommendation.** Retain opaque, server-resolved tokens. Before durable machine authorship, specify revocable credential instances, project grants, and when a durable Loom-local actor is warranted. Preserve issuer, acting credential and delegated authority in provenance. Treat historical attribution to an actual operator as unknown when all Loom observed was a bearer. **Early warning.** A credential label becomes the author ID, or Oscar, Lab and the Worker each issue identities for the same supposed agent. ### 4. Lifecycle transitions bound all copies of data and authority

**Evidence.** Finalization revokes live machine grants, removes invitations and memberships, deletes native versions and retains provenance. Native compression also has a compatibility projection in `documents.compression` and revision rows. The finalizer neither clears the projection nor explicitly deletes compression rows. A compression row bound to a deleted source version cascades, while a row with a null source reference is not covered by that cascade. Check-in values also survive in a separate table. Machine reads enforce the project deletion deadline before cron, whereas the native human body and project export queries have no equivalent deadline predicate. **Failure and cost.** Retained text can outlive the promised purge. Further public caches, external mirrors and search indexes compound deletion obligations. The repository describes reads during grace and shell behavior at finalization, leaving the intended human read behavior between deadline and cron worth resolving explicitly. **Recommendation.** Test and revise now. Classify check-in text explicitly, test shell storage as well as response status, and define the deadline contract per operation. Treat external downloads as irreversible disclosures. **Early warning.** A new projection has no purge test, or a read path agrees with revocation only after the scheduled job has run. ### 5. Whole-document revision and a small API can serve external collaboration

**Evidence.** A native update replaces the body and advances the version, with an existing source-version guard specifically for compression. The external roadmap proposes client-owned JSON schema and a narrow storage adapter. **Failure and cost.** Concurrent human or agent saves can hide earlier changes. Retries of ambiguous writes can duplicate effects. With higher write rates, full-body history, unpaginated machine lists and in-memory ZIP exports can create storage or latency pressure. If multiple external clients depend on raw Worker response shapes or both backends accept writes, changing semantics becomes a coordinated migration. **Recommendation.** Test conditional, idempotent writes on one resource before generalizing. Full-document revisions are viable for low-frequency work. Consider append-only commands for measured high-frequency structured workloads, and real-time merge only after evidence that asynchronous conflict handling fails. **Early warning.** Clients implement permanent dual writes, silently retry conflicts, or store application-specific entities in the core schema. ## 4. Three alternative trajectories

| Trajectory | Scope and benefit | Risks, dependencies and learning |
| --- | --- | --- |
| Conservative | Keep the Worker and D1. Consolidate operation policy where it already diverges, verify deletion and revocation, and document the contracts existing callers rely on. | Gives users little new functionality. Depends on settling cutoff and retention semantics and extending the populated fixtures. Shows whether the existing enforcement boundary can support another access path. |
| Incremental | Publish one explicitly opted-in project projection with selected current native documents. Keep human edits within existing membership and add conditional saves for the authoring pilot. | Risks disclosure through metadata, compression, linked items, caching or indexing. Depends on finalization and revocation semantics, copy/link consent and a narrow public response contract. Measures whether people find useful projects and whether revision conflicts materially hinder collaboration. |
| Exploratory | In fixtures or a disposable environment, have one external adapter and one agent operate on a single project-native JSON document. Compare a conditional replacement with an append-only command stream. Exercise revocation, rotation, concurrent edits, retries and provenance. | Prototype client code can diverge from real needs or accidentally become a permanent contract. Depends on an actual low-volume workflow, synthetic state, a rollback path and a single write authority per trial. Shows whether document-scoped grants or a durable actor are needed, and whether event operations beat conditional replacement for the workload. |

**Preferred sequence.** Begin conservatively with a bounded set of high-impact cases and move straight to an incremental publication pilot once those cases pass. A dedicated authorization service or relationship engine could help if Loom develops independently deployed policy consumers or genuinely recursive sharing relationships. At present, a policy service would still need agreement with D1 at the decisive write, increasing consistency and deployment costs. Likewise a separate Lab Worker/D1 deployment is a reasonable response to measured public workload or retention isolation needs, while application isolation can continue in the interim. ## 7. Open questions requiring human judgment

1. Should public project discovery expose only a catalog entry by default, selected bodies, or an intentional publishable snapshot? Who may publish, and can a contributor independently withdraw linked material from public view?
2. Does a first contribution grant durable membership, or should an open contribution remain separately attributable until the project accepts it? Which rights, if any, come with membership by default?
3. When an owner changes, should previous grants survive, require explicit reaffirmation, or expire automatically? Who can recover or disable a long-running agent after the sponsoring person leaves?
4. What does durable agent identity mean in Loom's first real workflow: a project-owned service actor, a human's delegate, or a cross-project actor? Who can link or recover that identity, and what provenance survives credential revocation?
5. What is the project-authorized retention policy for check-ins, summaries, public caches and integration-derived data? What cutoff should users expect between deadline and finalizer?
6. Which real project or external workflow will tell us whether publication or delegated writing is worth expanding? What evidence would justify feeding Loom events into THREAD, and which system could act on changes or withdrawals?
